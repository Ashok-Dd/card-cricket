# Backend (NestJS) — conventions

Read the repo root `CLAUDE.md` and `docs/` first. This file only covers backend-specific conventions.

## Stack notes (things that would otherwise surprise you)

- This project is **ESM** (`"type": "module"` in package.json). All relative imports need an explicit `.js` extension (`./foo.service.js`), even though the source file is `foo.service.ts` — that's normal for this Nest/TS-ESM setup, not a typo.
- Package manager is npm, but **`npm install` requires `legacy-peer-deps=true`** (already set in `.npmrc`) — plain `npm install` on this Nest 12 + Vitest 4 combo otherwise hits a real npm/arborist bug (`Cannot read properties of null (reading 'edgesOut')`) on peer-dependency resolution for `@vitest/browser-playwright`. If a fresh install ever fails with that exact error, it's this bug, not a real dependency conflict.
- Tests run on **Vitest**, not Jest (`npm test`, `npm run test:e2e`) — this repo's Nest CLI template ships that way.
- Lint is **oxlint** (`npm run lint`), not ESLint.
- **Prisma is pinned to 7.10.0**, not the `8.0.0-rc.*` that `npm view prisma` currently resolves as latest — that's a pre-release, don't let a `npm install prisma@latest` silently jump onto it. Prisma 7 also dropped `datasource.url` from `schema.prisma`; the connection is instead built at runtime via `@prisma/adapter-pg` in `src/prisma/prisma.service.ts`, and separately via `prisma.config.ts` for CLI/migrate commands. Both need `DATABASE_URL` in `.env`.
- Generated Prisma client output is `src/generated/prisma` (not the default `generated/prisma` at the repo root) — it has to live under `src/` because `tsconfig.build.json` sets `rootDir: ./src`, and Nest's build fails otherwise (`TS6059`). It's gitignored; run `npx prisma generate` after cloning or after touching `prisma/schema.prisma`.
- `ioredis` (v6): import the named `{ Redis }` export, not the default export — `import Redis from 'ioredis'` type-checks incorrectly ("Cannot use namespace 'Redis' as a type") under this project's `moduleResolution: nodenext`. `import { Redis } from 'ioredis'` is the correct, working form (see `src/redis/redis.service.ts`).
- **`@UseGuards(JwtAuthGuard)` (the bare class) breaks in any module other than `AuthModule`** with `Nest can't resolve dependencies of the JwtAuthGuard (?)... AuthModuleOptions`. `JwtAuthGuard extends AuthGuard('jwt')`, and Nest resolves a guard passed by class reference through the *consuming* module's own DI container, which doesn't have `AuthModuleOptions` (that only exists where `PassportModule.register(...)` was called, i.e. `AuthModule`). The fix used throughout this codebase is to pass an **instance**: `@UseGuards(new JwtAuthGuard())` — an already-constructed object needs no DI resolution. Always use `new JwtAuthGuard()`, never the bare class, when guarding a route outside `auth.controller.ts` (see `src/wallet/wallet.controller.ts`).
- **`npx prisma db seed` swallows the seed command's stdout** in this Prisma version — it always prints just "The seed command has been executed" regardless of what the script actually did (including if it silently errored). Don't trust that message; run the compiled script directly (`node dist/prisma-seed/seed.js`) when you need to see real output or debug a seed failure.
- `RedisService` uses `lazyConnect: true` and does **not** await a connection in `onModuleInit`. `REDIS_MOCK=true` swaps in `ioredis-mock` (used on this dev machine before real Redis was available) — same `.client` API either way. The live `GameState` blob (per-game shuffled piles, current turn, tie state) is stored there under key `game:{gameId}` — see `src/game/game-state.store.ts`.
- **Seed data is real Cricsheet player statistics** (`src/prisma-seed/generated/cricket-data.json`, committed, generated by `scripts/extract-cricket-data.mjs` + `scripts/fetch-player-images.mjs` from raw archives that are NOT committed — see [[real-cricket-data-pipeline]] in project memory for the extraction methodology, the ODI-folder data-quality bug, and why ODI is currently skipped). `seed.ts` bulk-inserts via client-generated UUIDs and 3 `createMany` calls, not per-row `create()` — a remote/serverless Postgres (this project now runs on Neon) makes thousands of sequential round trips genuinely slow (measured: over an hour vs. a few seconds bulk), not just a style preference.
- **WebSocket auth**: `GameGateway.handleConnection` reads a JWT from `socket.handshake.auth.token` and disconnects immediately on failure — there is no unauthenticated socket state. A connected socket auto-joins `user:{userId}` (for targeted per-player emits); it must separately emit `room:subscribe`/`game:subscribe` (server-verified against `RoomPlayer`/`GamePlayer` membership) to join a room's or game's broadcast channel. Any future guard with constructor dependencies used outside its home module needs the same `new SomeGuard()` treatment as `JwtAuthGuard` below.

## Local infra

`docker-compose.yml` at the repo root brings up Postgres (`localhost:5432`, db `card_cricket`, user/pass `postgres`/`postgres`) and Redis (`localhost:6379`) matching the defaults in `.env.example`. Run `docker compose up -d` from the repo root before `npm run start:dev`. (If Postgres is already running natively on the host on port 5432 with matching credentials, that works too — Prisma doesn't care whether it's the containerized or a native instance.)

## Production infra & deployment

This app now also runs against real hosted infrastructure: **Neon** (serverless Postgres) and **Upstash** (managed Redis) — see [[real-cricket-data-pipeline]] for how `.env` points at them. **Upstash's Redis URL must use `rediss://` (TLS)**, not `redis://` — the plain scheme fails to connect at all. Deployment target is **Render**, as a Docker web service (`apps/backend/Dockerfile`, root directory `apps/backend`; `render.yaml` at the repo root documents the service). `docker-entrypoint.sh` runs `prisma migrate deploy` then the seed script (idempotent via `alreadySeeded`) then starts the server — the runtime image does a full `npm ci` (not `--omit=dev`) because the `prisma` CLI and `dotenv` are devDependencies needed at container startup, not just at build time. The Docker build itself has not been verified locally (Docker Desktop's engine doesn't run reliably on this dev machine) — every step it runs was individually verified working directly on the host instead.

## Module layout

One folder per Nest module under `src/`, matching the module list in `docs/ARCHITECTURE.md` (`AuthModule UsersModule PlayersModule CardSetsModule CardsModule RoomsModule LobbyModule GameModule WalletModule RewardsModule AchievementsModule LeaderboardModule AdminModule`), plus `src/prisma` and `src/redis` as `@Global()` infra modules exported once from `AppModule`.

`GameModule` is the real-time + game-engine core: `GameGateway` (WebSocket surface, `src/game/game.gateway.ts`), `RealtimeService` (broadcast wrapper — `RoomsModule` imports `GameModule` one-directionally to use this; `GameModule` never imports `RoomsModule`, to avoid a circular dependency), `GameEngineService` (the actual rules — shuffle/deal/turn/comparison/tie/elimination/win, see `docs/GAME_RULES.md`), `GameLockService` (per-`gameId` async lock serializing mutations — single-instance only), and `GameStateStore` (Redis-backed live `GameState`). `GamesController` (`GET /games/:id`) is a plain-HTTP fallback for the same personalized snapshot `game:subscribe` returns over the socket.

Controllers exist for every module with a REST surface per `docs/ARCHITECTURE.md` (`/auth /users /players /card-sets /rooms /wallet /games`). `Rewards`, `Achievements`, `Leaderboard`, and `Admin` are still empty scaffolding — those weren't part of "make the app completely working" (see `docs/ROADMAP.md`'s deferred list) — don't add speculative business logic to them without a reason.

`RoomsService.start()` creates the `Game`/`GamePlayer` rows (status `WAITING`) then immediately calls `GameEngineService.startGame()`, which does the actual shuffle/deal/entry-deduction and flips everything to `IN_PROGRESS` — see that method's doc comment for the exact sequence.

## Server authority — the constraint that shapes every module

Every mutation to game state, card ownership, or coin balance must run through a service method that itself decides the outcome from data it owns (DB/Redis), never from a value the client sent. See root `CLAUDE.md` and `docs/GAME_RULES.md`. WebSocket event names live in `src/game/game-events.constants.ts` — keep them in sync with the Flutter client's expectations documented in `apps/mobile/CLAUDE.md`.

## Economy

Coin balance changes always go through the `coin_transactions` ledger (see `docs/ECONOMY.md` and the `CoinTransaction` model in `prisma/schema.prisma`), keyed by an idempotency key — never a bare increment/decrement on `Wallet.balance`. `WalletService`'s `applyDelta` private helper is the one place that actually mutates a balance; `creditWelcomeReward`/`deductGameEntry`/`creditGameReward`/`refundGameEntry` are all thin wrappers over it with their own idempotency key scheme (`welcome:{userId}`, `entry:{gameId}:{userId}`, `reward:{gameId}:{userId}`, `refund:{gameId}:{userId}`). A match's winner gets one combined `GAME_REWARD` transaction covering both the redistributed entry pool and the flat `ECONOMY_MATCH_WIN_BONUS_COINS` completion bonus — not two separate transactions, since `creditGameReward`'s idempotency key is per-`(gameId, userId)`, not per-reward-type.
